# FOC L4 代码理解与架构答辩记录

## 1. 文档目的

本文记录对 `main.c`、`app_debug.c`、测量模块和通信输出链路的代码理解过程。

本文重点区分以下几类结论：

- 代码当前实际做了什么；
- 设计上为什么这样做；
- 当前已经验证的内容；
- 当前仍然只是推断或待验证的内容；
- 后续是否值得重构。

在完成整体代码理解前，暂不进行大范围架构重构。

## 2. 当前控制链位置

当前项目仍处于 V/F + SVPWM 阶段，还没有进入完整的 Id/Iq 电流闭环：

```text
TIM1 CH4 触发 ADC
    -> ADC1 读取三相电流
    -> 三电阻按 sector_applied 选择两相并计算第三相
    -> 软件过流判断
    -> V/F 状态更新
    -> 反 Park 计算电压矢量
    -> SVPWM 计算 sector_next 和比较值
    -> 写入 PWM 比较寄存器
    -> ADC/PWM 下一周期继续运行
```

调试通信不属于快速控制链：

```text
主循环
    -> comm_cmd_poll
    -> 解析 start、stop、freq 命令
    -> 生成普通 VOFA 输出
```

Scope 输出当前由 ADC 控制回调触发，但实际发送仍经过 ringbuffer、DMA、串口和 VOFA+。

## 3. `main.c` 职责分析

### 3.1 当前实际职责

`main.c` 当前承担应用层组合根的职责，包含：

- 系统和外设初始化；
- V/F、SVPWM、测量、故障和通信对象定义；
- 各模块初始化参数绑定；
- 串口命令回调绑定；
- 功率级启停回调；
- 电流零点校准流程；
- ADC 注入转换完成入口；
- V/F、SVPWM、过流保护的快速控制链连接。

因此，`main.c` 过于集中，但问题不只是代码行数多，而是初始化、应用绑定、快速控制和调试输出同时存在。

### 3.2 当前判断

`main.c` 仍然可以作为应用层组合根，不需要马上拆成大量对象或状态机。

性能关键不在于文件数量，而在于 ADC 快速路径中是否包含阻塞操作和不必要的逻辑。

### 3.3 后续可选拆分

后续可以考虑轻量拆分：

```text
main.c
    -> 系统入口、顶层初始化和任务启动

app_init.c
    -> 应用模块初始化和句柄绑定

app_control.c
    -> ADC 快速控制链

app_debug_binding.c
    -> 串口命令和功率级回调
```

拆分前必须先确认：

- 各句柄的所有权；
- ADC 中断修改哪些状态；
- 主循环读取哪些状态；
- 哪些回调属于应用层；
- 哪些硬件接口只能由应用层调用。

## 4. ADC 快速路径和主循环

### 4.1 ADC 回调中的内容

当前 ADC1 回调中包含：

- 读取三相电流 ADC 原始值，单位为 ADC count；
- 使用 `sector_applied` 进行三电阻选相和第三相计算；
- 软件过流判断，单位为 A；
- V/F 状态更新，控制周期约为 `1 / 16 kHz = 62.5 us`；
- SVPWM 计算；
- PWM 比较值更新，单位为 timer tick；
- Scope 数据提交。

这些操作与 PWM/ADC 同步，因此不能整体移动到主循环。

### 4.2 可以放慢的内容

ADC3 回调目前主要保存 BEMF/相端电压和 VBUS 原始 ADC 值，单位为 ADC count。

后续电压换算和 VOFA 普通输出可以放在主循环中，因为它们暂时没有直接参与快速控制决策。

快慢路径可以理解为：

```text
快速路径：采样、过流、控制计算、PWM更新
慢速路径：电压换算、状态查询、命令解析、普通监控输出
```

## 5. PWM 影子寄存器与 Scope 输出

### 5.1 已确认的部分

`hw_pwm_set_duty()` 将新的比较值写入定时器比较寄存器。若 TIM1 对应通道启用了预装载/影子机制，新的比较值会在定时器更新事件按硬件规则生效。

因此，后续 Scope 数据填充不会改变已经写入的 PWM 比较值。

### 5.2 仍需区分的两个问题

影子寄存器解决的是：

```text
比较值何时从预装载寄存器转移到有效寄存器
```

它不能解决：

```text
ADC 中断整体执行时间是否过长
```

当前顺序为：

```text
svpwm_update
    -> hw_pwm_set_duty
    -> app_debug_on_pwm_update
```

`app_debug_on_pwm_update()` 接收到的是本次计算出的 PWM 比较值，也就是准备供下一周期使用的数据，不是本次 ADC 采样之前已经生效的旧 PWM。

如果 Scope 发送函数阻塞等待串口发送完成，仍可能导致下一次 ADC 控制回调不能及时执行，产生控制周期延迟或抖动。

当前需要继续确认：

- `comm_scope_send_scope()` 是否只写入 ringbuffer；
- 是否会等待 DMA 或串口发送完成；
- ringbuffer 满时是丢帧、返回错误还是阻塞；
- DMA 是否连续工作。

## 6. `app_measurement_get()` 无限重试风险

### 6.1 当前机制

测量模块使用 `sequence` 判断多字段快照是否一致：

```text
sequence 为奇数：写入进行中
sequence 为偶数：一次写入结束
```

主循环读取时：

```text
读取起始 sequence
    -> 读取多个测量字段
    -> 读取结束 sequence
    -> 两次相同且为偶数，接受快照
    -> 否则重新读取
```

这样可以避免主循环读取到一半时被 ADC 中断更新，最终得到半新半旧的数据。

### 6.2 为什么即使 ADC 优先级更高仍然有意义

问题不是主循环会抢占 ADC，而是：

```text
主循环读取字段 A
    -> ADC 中断更新全部字段
    -> 主循环继续读取字段 B
```

主循环可能得到来自不同采样时刻的数据。`sequence` 用来检测这种跨中断读取的不一致。

### 6.3 无限循环风险

当前 `app_measurement_get()` 使用无限重试，理论上存在：

- `sequence` 永久保持奇数；
- 读取期间始终发生更新，无法取得稳定窗口；
- 上游异常导致提交状态未恢复；
- 主循环永久卡在测量读取函数中。

一旦发生，主循环中的以下任务都会停止：

- 串口命令解析；
- `stop` 命令处理；
- 普通 VOFA 输出；
- 其他后台任务。

### 6.4 当前推荐方案

推荐后续改为有限重试：

```text
尝试读取快照
    -> 成功：返回 0
    -> 失败：重试，直到达到上限
    -> 超过上限：返回错误
    -> 上层跳过本次输出，主循环继续运行
```

不建议当前使用关闭中断保护整个复制过程，因为会增加 ADC 控制链的延迟。

后续方案比较：

| 方案 | 优点 | 缺点 | 当前建议 |
|---|---|---|---|
| 有限重试 | 改动小，不阻塞主循环 | 本次可能没有新数据 | 当前优先 |
| 关闭中断后复制 | 简单，快照完整 | 延迟 ADC 中断 | 不推荐 |
| 双缓冲快照 | 一致性和实时性好 | 结构更复杂 | 电流环阶段考虑 |

尚未决定的参数包括：

- 最大重试次数；
- 失败时是否跳过本次 VOFA 输出；
- 是否保留上一帧有效数据；
- 是否增加快照失败计数。

### 6.5 当前结论

测量快照建议采用有限重试，失败后返回错误并跳过本次显示，不使用未标记的半新半旧数据，也不因一次读取失败而关闭 ADC。连续失败统计、采样异常升级和控制模式下的容错边界，统一记录在第 8.6 节。

需要明确区分“测量快照读取失败”和“ADC控制采样异常”：

```text
current_snapshot_get() 失败
    -> 主循环没有取得一致的显示快照
    -> 不代表ADC控制采样失败
    -> 不应直接停止FOC、V/F或关闭功率级
    -> 可跳过本次普通VOFA输出
    -> 可累计并上报后台测量接口错误

ADC控制采样异常
    -> 快速控制链的输入不可信
    -> 可能影响过流保护和FOC电流环
    -> 按第8.6节的严格策略处理
```

即使 `current_snapshot_get()` 读取失败，只要 ADC中断中的电流采集和软件过流判断仍然正常，控制链也不应因为普通显示读取失败而停机。快照接口属于观测和后台诊断链路，ADC控制采样属于实时控制和安全链路，二者故障等级不同。

## 7. VOFA+ 3 Mbps 卡顿问题

### 7.1 完整数据链路

```text
控制回调产生数据
    -> JustFloat 组帧
    -> TX ringbuffer
    -> DMA
    -> UART
    -> USB转串口
    -> PC 串口驱动
    -> VOFA+ 解析
    -> VOFA+ 绘图刷新
```

卡顿不应只归因于 VOFA+，也可能发生在发送端或缓冲区。

### 7.2 带宽估算

三通道 JustFloat 假设：

```text
3 × 4 字节 float32 + 4 字节帧尾 = 16 字节/帧
```

若按 16 kHz 发送：

```text
16 × 16000 = 256 kB/s
```

按照 UART 8N1 约 10 bit/byte 估算：

```text
256 × 10 × 8 = 2.048 Mbps
```

这已经接近 3 Mbps 的实际可用范围，还没有计入 USB 转串口、DMA、驱动和上位机处理开销。

20 通道时：

```text
20 × 4 + 4 = 84 字节/帧
84 × 16000 = 1.344 MB/s
```

这明显超出 3 Mbps 串口的稳定传输能力。

### 7.3 当前可能原因

- Scope 输出频率等于 PWM 频率；
- JustFloat 每帧开销较大；
- TX ringbuffer 满时可能阻塞或丢帧；
- DMA 分块或重启策略不理想；
- USB 转串口实际吞吐低于标称值；
- VOFA+解析或绘图线程处理不过来；
- 发送频率、通道数和波特率没有独立配置。

### 7.4 合理解决方向

控制采样和通信发送不应绑定为同一个频率：

```text
控制采样频率：16 kHz
数据发送频率：1 kHz 或更低
上位机显示频率：100~500 Hz
```

在修改前，应先确认：

- 发送函数是否阻塞；
- ringbuffer 满时的处理方式；
- DMA 是否连续发送；
- 实际发送帧率；
- 每帧通道数；
- 是 VOFA+显示卡顿，还是串口接收已经停止。

## 8. 后期架构设计：应用层、控制算法和观测器

### 8.1 当前讨论提出的方向

后续可以考虑使用一个外层 `motor` 应用对象，统一组织控制对象和状态对象：

```text
motor
├── ctrl
│   ├── V/F
│   ├── I/F
│   └── FOC
├── observer
│   ├── SMO
│   ├── 磁链观测器
│   ├── PLL
│   └── HFI
└── status
    ├── 运行状态
    ├── 故障状态
    └── 诊断数据
```

控制算法可以组合或切换，但任意时刻应只有一个算法拥有当前控制输出。建议控制算法输出统一的电压矢量或调制指令，由 SVPWM 完成调制，再由硬件 PWM 接口执行：

```text
控制算法
    -> 统一控制输出
    -> SVPWM
    -> 硬件 PWM 接口
    -> 定时器和功率级
```

控制算法不应直接访问定时器寄存器，SVPWM 也不应把具体定时器实现暴露给上层。

### 8.2 模块边界判断

- `ctrl` 负责控制策略和控制量生成；
- `observer` 负责从采样数据估算角度、速度、磁链或位置；
- `status` 负责反映电机实际运行状态、故障码和诊断信息；
- SVPWM 负责电压矢量到三相占空比的转换；
- 硬件 PWM 层负责定时器和功率级执行；
- `app_debug` 通过快照或访问接口获取数据，不直接读取控制模块内部成员。

PLL通常属于角度或速度估算链路。HFI同时包含高频注入和响应估计，后续可放在观测器体系下，但需要明确注入控制量与普通控制算法之间的所有权，不能让多个模块同时修改最终PWM指令。

### 8.3 当前不立即重构的原因

当前项目仍处于 V/F + SVPWM 和实机验证阶段，立即引入完整 `motor` 外层对象可能带来：

- 句柄和状态所有权重新分配；
- ADC快速路径增加间接调用；
- 调试输出接口需要重新绑定；
- 控制算法切换状态机提前复杂化；
- 为了形式上的分层增加不必要的抽象和栈开销。

因此问题13归类为 **P2：后期控制架构重构**。当前先保持现有实现，等电流采样、软件过流和基本控制链稳定后，再根据实际新增算法数量决定是否拆分。

### 8.4 后续设计约束

后续重构必须先明确：

1. 控制算法的唯一输出所有权；
2. SVPWM与硬件PWM之间的接口和单位；
3. 观测器输入数据的采样时刻和有效性；
4. `status`中哪些字段由中断更新、哪些字段由主循环读取；
5. `app_debug`访问快照的生命周期和失败策略；
6. 算法切换时的停机、过渡和故障保护行为。

在这些问题没有确定前，不建立“大而全”的通用电机对象。

### 8.5 故障标志与外层故障管理职责

SVPWM模块内部的 `svpwm.fault` 只能表示调制算法检测到了异常，不能单独承担完整的系统保护职责。故障处理至少需要区分两个层次：

```text
SVPWM算法故障：报告调制计算异常
外层故障管理：决定系统是否继续运行
```

系统状态至少应包含：

```text
运行允许状态
故障锁存状态
```

其中，`svpwm.fault` 负责报告算法异常，外层故障管理负责决定：

- 是否关闭功率级 SD；
- 是否禁止后续 PWM 比较值更新；
- 是否允许串口 `start` 命令生效；
- 是否保留 ADC 触发和故障后测量；
- 是否允许执行故障复位；
- 是否记录故障上下文。

推荐的故障链为：

```text
检测算法异常
    -> 记录故障上下文
    -> 锁存故障状态
    -> 关闭功率级
    -> 禁止后续PWM更新
    -> 根据策略保留ADC和通信
    -> 禁止自动重新start
    -> 等待明确的故障复位
```

故障现场应记录最近一次有效生效的 PWM、当前控制输入、VBUS、VDDA、ADC原始值、sector、故障码和时间信息。不能为了保存异常矢量而继续输出包含 NaN、越界值或未知状态的占空比。

不同故障类型不能只依靠一个错误码区分，故障上下文还应服务于后续定位：

SVPWM调制异常重点记录：

- `svpwm.fault`；
- `v_alpha`、`v_beta`；
- VBUS和VDDA；
- `sector_applied`；
- 最近一次有效的 PWM CCR；
- 当前控制输入是否包含 NaN 或 Inf；
- 故障发生时间。

软件过流重点记录：

- 三相 ADC 原始值；
- VREFINT和VDDA；
- 三相电流零点偏移；
- 三相换算电流；
- 电流重构前后的结果；
- `sector_applied`；
- 当前电流峰值；
- 连续过流计数；
- VBUS；
- 故障发生时间。

两类故障最终可以执行统一的功率级保护动作，但故障检测前的现场保存必须有所区别。错误码只能说明“发生了哪一类故障”，完整上下文才能帮助判断故障是由控制输入、调制计算、采样链路还是实际电流超限引起的。

`stop`、故障停机和故障复位的职责不同：

- `stop`：用户或上层流程主动发起的正常停机；
- 故障停机：检测到异常后立即关闭功率级，优先保障硬件和电机安全；
- 故障复位：确认故障原因消失后，清除故障锁存，使系统重新具备启动资格。

故障复位不能隐含在 `start` 命令中，否则串口误操作或上位机重试可能导致故障后自动重启。

### 8.6 采样异常处理不能耦合 V/F

当前项目处于 V/F 阶段，因此可以暂时采用“电流采样无效时跳过电流相关处理、继续运行 V/F 和 SVPWM”的验证策略。但这只能是当前控制模式下的策略，不能成为采样模块的固定行为。

后续项目的主要控制方式将逐步转向 I/F 和 FOC。届时电流是核心控制输入，电流采样异常会直接影响：

- 电流环反馈；
- Clarke/Park 变换；
- `Id/Iq` 控制器；
- 限流和软件过流保护；
- 转矩控制；
- 观测器输入；
- 控制算法切换条件。

因此不能在 ADC 采样模块中写入类似“V/F下继续运行”的固定逻辑。应保持以下职责分离：

```text
采样层
    -> 采集原始数据
    -> 判断数据是否有效
    -> 记录采样质量和失败计数
    -> 输出统一的采样快照

控制算法层
    -> 根据当前控制模式解释采样有效性
    -> 决定继续、降级、保持或停止控制计算

故障管理层
    -> 根据连续失败和故障等级决定是否关闭功率级
    -> 锁存故障并禁止自动启动
```

不同控制模式可以拥有不同的降级策略，但必须通过统一的采样有效性接口获得信息：

| 控制模式 | 电流采样无效时的初步策略 |
|---|---|
| V/F | 电流不参与控制计算；其他有效控制链可短暂继续；连续失败后停机 |
| I/F | 根据电流反馈是否参与限流和转矩控制决定降级；不能无条件使用旧值 |
| FOC | 电流反馈无效通常不能继续正常闭环；应快速降级或停机 |
| 观测器 | 根据观测器输入要求决定是否冻结、降权或退出观测状态 |

这里的“继续运行”只表示当前模式在短时间内仍可执行控制，不表示采样异常被忽略。采样模块不得直接调用 V/F、I/F 或 FOC 的具体函数，也不得假设系统永远只使用 V/F。

后续接口设计应优先考虑以下统一字段：

```text
current_sample_valid
current_sample_age
current_sample_error_code
current_sample_error_count
current_sample_timestamp
```

这样，新增 I/F、FOC 或观测器时只需实现对应的异常策略，不需要修改底层 ADC 采样和异常记录逻辑。

#### FOC/I/F下的采样异常容错边界

需要区分两类异常：

```text
测量快照异常
    -> 主循环读取时没有取得一致数据
    -> 主要影响VOFA和后台显示

ADC控制采样异常
    -> ADC触发、转换、DMA或采样窗口异常
    -> 直接影响快速控制链和软件过流监控
```

测量快照异常通常允许有限重试。重试失败后跳过本次显示，不能阻塞主循环，也不应直接影响 FOC 或 I/F 控制。

ADC控制采样异常则需要采用更保守的策略。FOC高度依赖当前电流反馈，不能使用上一周期电流冒充当前电流，也不能让无效电流继续更新 Clarke/Park、`Id/Iq` 控制器或软件过流判断。

在没有独立硬件过流保护，或者无法确认采样窗口和ADC状态可靠时，当前建议为：

```text
一次确认的ADC控制采样异常
    -> 标记当前采样无效
    -> 停止依赖该采样的控制计算
    -> 请求故障停机
    -> 锁存故障
    -> 关闭功率级
```

只有在未来同时满足以下条件时，才考虑允许极短的容错窗口：

- 能准确识别本次数据确实无效；
- 有独立硬件过流保护，或已证明短时风险可控；
- 有 `sample_valid`、采样年龄和连续失败计数；
- 容错周期有明确上限；
- 无效期间不更新电流环积分项；
- 不使用旧电流冒充当前反馈；
- 连续失败会立即升级为故障锁存；
- 故障锁存后禁止 `start` 自动重启。

I/F不能统一视为可以容错。纯开环 I/F 可能暂时不依赖电流反馈，但电流采样异常仍会导致限流和软件过流监控失效；带电流限制或电流闭环的 I/F，应按照 FOC 的严格策略处理。

因此，后续控制模式的处理原则为：

| 控制模式 | ADC控制采样异常的初步策略 |
|---|---|
| 当前 V/F | 可作为当前验证阶段的临时策略，但必须累计失败并升级故障 |
| 纯开环 I/F | 仍需考虑电流监控失效，不能无限继续运行 |
| 带电流反馈的 I/F | 按电流反馈控制处理，不使用无效数据更新控制器 |
| FOC | 默认一次确认异常即请求停机；只有满足完整安全前提后才考虑极短容错 |

这里的自动恢复也需要分级：未升级为锁存故障的瞬态异常可以在采样恢复后继续运行；一旦已经进入故障锁存，即使 ADC 恢复正常，也必须人工检查并执行明确的故障复位，不能自动重新启动。

### 8.7 后期重构的数据边界与访问约束

第20题的讨论进一步明确了后续重构中的数据生产者、消费者和所有权边界。

#### 数据生产者

ADC控制中断负责产生或更新快速控制链需要的数据：

- 三相电流采样值；
- 三相相端电压或反电动势采样值；
- 母线电压采样值；
- 采样有效性和采样错误计数；
- 当前控制状态和必要的采样时间信息；
- 根据本次控制计算得到的下一周期 PWM CCR。

ADC中断可以更新这些数据，但不能调用阻塞通信接口，也不能把调试输出反向耦合进控制计算。

#### 数据消费者

主循环主要读取测量快照、控制状态、故障状态和 PWM 观测数据，用于：

- 命令处理；
- 普通 VOFA 输出；
- 状态查询；
- 后台诊断；
- 非实时故障记录。

主循环可以读取 CCR 用于显示，但应读取 PWM 观测快照，而不是直接访问正在由 ADC中断更新的控制对象内部成员。

#### 访问方式

后续优先采用只读 API 获取数据，例如：

```text
app_measurement_get()
app_control_status_get()
app_fault_snapshot_get()
app_pwm_observe_get()
```

API返回的是一致的观测快照，不直接暴露内部句柄、硬件对象或可写控制成员。直接结构体赋值只有在结构体本身是只读快照、生命周期明确且具有一致性保护时才允许使用。

#### 快照保护范围

需要同一采样时刻语义的数据应放入同一个快照，或使用同一套一致性保护：

- 三相电流；
- 三相相端电压；
- VBUS和VDDA；
- `sector_applied`；
- ADC原始值；
- 采样有效标志；
- 故障计数和时间戳。

PWM CCR属于下一周期调制观测数据，可以单独建立 PWM 快照。它与电流采样快照不一定属于同一语义时刻，不能仅因为同时发送就认为二者天然一致。

#### 共享 `sequence` 的局限

当前测量对象使用一个共享的 `sequence` 保护电流、相端电压、VBUS和VREFINT等数据。它可以判断主循环复制期间是否发生过更新，但不能表达不同 ADC 数据源之间的采样时刻关系。

当前正常运行时，ADC中断优先级最高，单次快照读取期间不可能发生 `sequence` 完整回绕，因此计数器溢出不是当前工程的实际问题。真正需要改进的是不同采样源不应长期共用同一个快照计数器。

后续建议按数据源拆分：

```text
current_sequence
    -> 三相电流原始值
    -> sector_applied
    -> 电流采样有效状态

voltage_sequence
    -> BEMF/相端电压
    -> VBUS

vrefint_sequence
    -> VREFINT
```

如果VREFINT只作为电压换算依据，也可以将其纳入电压快照。对应的读取接口可以拆分为：

```text
current_snapshot_get()
voltage_snapshot_get()
```

这样可以避免把不同采样频率、不同触发源的数据强行包装成同一物理时刻的完整快照。

计数器使用 `uint8_t` 在当前短读取窗口下可以工作，但每增加2次后128组就会回绕，扩展余量较小。后续优先考虑 `uint16_t`，在空间开销几乎可忽略的情况下提供更大的回绕间隔。计数器拆分的主要目的，是明确数据源和快照语义，而不是单独解决溢出问题。

#### 调试访问边界

`app_debug.c`可以请求调试所需的数据，但不应直接访问：

- PWM硬件句柄；
- ADC/DMA句柄；
- 故障管理内部可写状态；
- 控制器积分器和内部中间变量；
- 正在由中断修改的非快照结构；
- 可以被调试代码误修改的控制成员。

调试模块获取的是只读观测数据，而不是控制模块内部对象的所有权。即使为了定位问题需要发送更多字段，也应通过明确的观测 API 扩展，不应通过暴露整个内部结构解决。

故障状态的检测、锁存、复位和应用层执行职责统一见第 8.5 节。本节只补充数据访问约束，不重复定义故障管理流程。

本节属于后期重构设计约束，当前不代表上述 API 和快照结构已经全部实现。

## 9. 当前结论

目前不立即进行代码重构，先完成对 `main.c`、`app_debug.c`、`app_measurement.c` 和通信发送链路的理解。

当前已形成的理解：

- `main.c` 是应用层组合根，但职责过多；
- ADC 回调承载同步控制链，不能整体移入主循环；
- BEMF/VBUS 原始采样和后续换算可以走慢速路径；
- PWM 影子寄存器不等于 ADC 中断执行时间不受影响；
- `sequence` 用于多字段快照一致性，主循环读取时仍有意义；
- 无限重试存在主循环永久阻塞风险；
- VOFA+卡顿需要按带宽、缓冲、DMA和上位机链路逐层定位；
- 采样快照失败应采用有限重试和错误返回，属于后续 P1 任务；
- `motor`、控制算法、观测器和状态对象的统一架构属于后续 P2 设计；
- 本文中的后期重构方案仍属于设计结论，尚未全部修改代码或完成对应实机验证；已完成的当前版本修复和实机验证应以代码、提交记录和其他验证文档为准。

## 10. 实现优先级

| 优先级 | 事项 | 当前状态 | 实现条件 |
|---|---|---|---|
| P0 | 功率级安全链、故障锁存、禁用PWM后的ADC连续性 | 已完成关键修复，持续实机验证 | 任何新增控制功能都不能破坏 |
| P1 | 采样快照有限重试、失败统计和故障升级 | 待实现 | 先确定重试上限和失败策略 |
| P1 | ADC采样有效窗口和动态触发时序 | 当前固定触发点 | 进入闭环或扩大调制度前验证 |
| P1 | 电流增益和采样链路标定 | 已具备零点校准基础 | 有电流钳或可靠负载条件时进行 |
| P2 | `motor` 外层对象与控制算法统一接口 | 后期设计 | 现有控制链稳定且新增算法确有需求 |
| P2 | 观测器体系和算法切换框架 | 后期设计 | 明确控制量所有权和切换策略后进行 |
| P2 | 通信发送与控制采样彻底解耦 | 已完成问题分析 | VOFA+高通道高速输出需求再次出现时处理 |

优先级含义：

- **P0**：直接关系到功率级和硬件安全，必须优先处理；
- **P1**：影响控制正确性、数据一致性或闭环可靠性，应在进入下一阶段前完成；
- **P2**：属于架构演进和扩展能力，当前功能稳定后再实施。
